# Отчёт: анализ сетевого трафика (Wireshark)

| Файл | Интерфейс | Содержимое |
|---|---|---|
| [`capture.pcapng`](capture.pcapng) | `happ-xray` (TUN-адаптер VPN) | основной дамп: HTTP-запросы к httpbin.org, HTTPS к api.github.com, DNS (57 пакетов) |
| [`capture-wifi-vpn.pcapng`](capture-wifi-vpn.pcapng) | «Беспроводная сеть» (Wi-Fi) | те же запросы, видимые на физическом интерфейсе, внутри VPN-туннеля (542 пакета) |

## Как выполнялся захват

1. Запущен захват в Wireshark (tshark 4.6.9).
2. Во время захвата выполнены запросы:
   ```bash
   curl -v http://httpbin.org/get
   curl -v -X POST http://httpbin.org/post -d "name=test"
   curl -v http://httpbin.org/status/404
   curl -v https://api.github.com
   ```
   Запросы к `http://` нужны, чтобы методы и коды ответов были видны открытым текстом.
3. Дамп сохранён в формате pcapng. В основной дамп `capture.pcapng` попал только трафик эксперимента, отобранный фильтром:
   `ip.addr == 3.221.253.123 || ip.addr == 140.82.121.5 || dns.qry.name == "api.github.com"`.

### Почему захватов два

На машине работает VPN-клиент (Xray) в TUN-режиме: весь трафик направляется на виртуальный адаптер `happ-xray` и уходит в интернет зашифрованным туннелем.

Первый захват был снят на Wi-Fi-интерфейсе (`capture-wifi-vpn.pcapng`). В нём **нет ни одного HTTP-пакета** и ни одного DNS-запроса к httpbin.org или github.com: фильтр `http` ничего не находит. Весь обмен выглядит как TLS-сессии к одному адресу `142.91.159.28:443`, то есть к VPN-серверу.

Поэтому захват повторён на интерфейсе `happ-xray`, где трафик виден до шифрования туннелем.

## Фильтры отображения

| Фильтр | Назначение |
|---|---|
| `http` | только HTTP-запросы и ответы |
| `tls` или `tcp.port == 443` | HTTPS-трафик |
| `http \|\| tls` | HTTP и HTTPS вместе |
| `http.request` | только запросы |
| `http.response.code >= 400` | только ошибочные ответы |
| `tls.handshake.extensions_server_name contains "github"` | TLS-сессии к api.github.com по SNI |
| `dns` | DNS-запросы и ответы |

Для проверки также использовались Statistics → Conversations → IPv4 и Statistics → Protocol Hierarchy.

## Результаты

### IP-адреса, участвовавшие в обмене

Основной дамп (`capture.pcapng`, интерфейс `happ-xray`):

| Узел | IP-адрес | Роль |
|---|---|---|
| Моя машина (адрес на TUN-адаптере VPN) | `172.19.0.1` | клиент |
| httpbin.org | `3.221.253.123` | сервер, HTTP, TCP-порт 80 |
| api.github.com | `140.82.121.5` | сервер, HTTPS, TCP-порт 443 |
| DNS-резолвер VPN-клиента | `172.19.0.2` | разрешение имён, UDP-порт 53 |

Дамп с Wi-Fi (`capture-wifi-vpn.pcapng`):

| Узел | IP-адрес | Роль |
|---|---|---|
| Моя машина (Wi-Fi) | `192.168.0.127` | клиент |
| VPN-сервер | `142.91.159.28` | все пользовательские данные идут сюда по TLS, порт 443 |
| Cloudflare DNS | `1.1.1.1` | DNS-over-HTTPS, порт 443 |
| Домашний роутер | `192.168.0.1` | шлюз, служебный трафик (SSDP, mDNS, NBNS) |

### HTTP-методы

| Кадр | Метод | URI | Хост | User-Agent |
|---|---|---|---|---|
| 4 | GET | `/get` | httpbin.org | curl/8.6.0 |
| 12 | POST | `/post` | httpbin.org | curl/8.6.0 |
| 20 | GET | `/status/404` | httpbin.org | curl/8.6.0 |

Итого: **GET × 2, POST × 1**.

Запрос к `https://api.github.com` тоже был, но его метод (GET) в дампе не виден, потому что он передаётся внутри TLS.

### Коды ответов сервера

| Кадр | Код | Значение | Ответ на запрос |
|---|---|---|---|
| 6 | 200 | OK | `GET /get` |
| 14 | 200 | OK | `POST /post` |
| 22 | 404 | Not Found | `GET /status/404` |

Код ответа api.github.com зашифрован и в дампе не виден.

### HTTPS: что видно без расшифровки

Обмен с api.github.com (фильтр `tls`):

- **Кадры 25–28 (DNS).** Сначала идёт запрос имени `api.github.com`. В ответе приходит адрес `140.82.121.5`.
- **Кадр 32 (Client Hello).** В открытом виде виден SNI `api.github.com` и список поддерживаемых версий TLS 1.0–1.3.
- **Кадр 34 (Server Hello).** Сервер выбрал **TLS 1.3** и шифр `TLS_AES_128_GCM_SHA256` (`0x1301`).
- **Дальше идут 9 записей `Application Data`.** HTTP-метод, URI, заголовки, тело и код ответа зашифрованы.

DNS-запрос к httpbin.org в дамп не попал, потому что адрес был взят из кэша ОС.

### Выводы

1. **HTTP передаёт всё открытым текстом.** Без расшифровки видны метод, URI, заголовки (включая User-Agent), тело запроса (`name=test`) и код ответа. Любой узел на пути может их прочитать или подменить.
2. **HTTPS раскрывает только метаданные соединения.** Видны IP-адреса, порт 443, время и объём обмена, а также имя сайта в SNI из Client Hello. Сами запросы и ответы зашифрованы (здесь TLS 1.3).
3. **Интерфейс захвата нужно выбирать с учётом VPN.** На физическом интерфейсе при работающем VPN видно только «машина ↔ VPN-сервер». Ни адресов назначения, ни DNS, ни протоколов прикладного уровня там нет. Чтобы анализировать реальный трафик приложений, захват нужно вести на TUN-адаптере VPN (или отключить VPN на время захвата).
